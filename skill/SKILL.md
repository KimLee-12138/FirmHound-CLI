# 路由器固件漏洞挖掘与验证 Agent Skill

面向任意 Linux 路由器固件（Tenda / Netgear / TP-Link / 各类嵌入式 Linux），在**本地、授权、教学**环境下，从固件镜像一路走到「有证据支撑的漏洞候选 + 非武器化验证」。全程只作用于本地 QEMU/FirmAE 仿真环境，不触碰任何真实设备或公网目标。

本 Skill 不服务某一个具体 CVE，而是沉淀两个已验证案例（Tenda AC15 / CVE-2020-10987 命令注入、Netgear R7000 系列分析）中可复用的共性方法：一套「怎么安全地做」的流程骨架，加一套「怎么挖得更深」的技术引擎。

---

## 0. 安全与授权门（硬门，全局约束）

开始前用一句话确认：**目标、固件/软件版本、实验网络是否属于用户或已获授权**。若目标是公网、未知设备、第三方生产系统，停止主动触发，只做静态分析或给出安全的复现建议。

**全局拒绝清单（所有阶段都不得越界）：**

- 不生成 RCE payload、GOT/PLT 覆写、后门/telnet 开启、root shell 自动化。
- 不窃取凭据、不持久化、不横向移动、不绕过真实目标认证。
- 验证仅用无害探针（`id`、`uname -a`），只为确认 sink 可达性，**不是构造利用链**。
- 若用户只需要判断漏洞是否存在，用静态证据、崩溃特征或非破坏性输入替代攻击链。

---

## 1. 实验卡片与基线

在执行任何命令前，先写一张简短实验卡片，避免把「进程启动了」误当作「漏洞复现/挖掘成功」。

```text
目标：型号 / 组件 / 入口 / 问题编号（若有）
版本：固件版本、文件名、SHA256、来源 URL
授权：自有 / 靶场 / 书面授权；网络隔离方式
假设：预期输入、处理路径、可观察现象
成功标准：最小可重复输入 + 明确现象 + 可定位证据
失败标准：超时、服务未启动、地址/版本不一致或仅有猜测
```

把每一步拆成「动作 → 证据 → 判断」。例如「读取 `readelf -r` → 保存重定位表 → 判断导入符号是否与参考版本一致」。

---

## 2. 固件获取与解包

### 2.1 基线哈希与只读保存

1. 优先使用厂商官方来源，记录 URL、下载时间、文件大小和 SHA256。**不要把文件名当作版本证明。**
2. 将原始固件只读保存；所有切片、解包和修补放 `work/`，报告放 `reports/`，命令输出放 `logs/`。

```bash
sha256sum firmware/<image>
file firmware/<image>
binwalk -Me firmware/<image> 2>&1 | tee logs/binwalk_extract.log
ROOT=<解出的 squashfs-root>
```

### 2.2 解包失败时的降级路径

自动工具无输出 ≠ 固件不可分析。按顺序保留证据：

1. 查看文件头、厂商标记和 `strings` 输出。
2. 搜索已知文件系统魔数（如 SquashFS `hsqs`），记录偏移、切片命令和 `file` 识别结果。
3. 用 `unsquashfs` 展开到明确命名的目录，记录压缩格式、错误和最终 rootfs 路径。
4. 若存在多个候选目录，用 `usr/sbin/httpd`、`bin/busybox`、`etc/init.d`、`www`、`lib` 等标记评分，并说明选择理由。

不要覆盖原始镜像，也不要把未验证的目录当成 rootfs。

---

## 3. 攻击面盘点

对 rootfs 生成以下清单：

- Web 服务二进制、CGI/脚本、静态资源和配置。
- 启动脚本、守护进程、监听端口、设备节点和运行时目录。
- **认证边界**：哪些路径需要登录，哪些路径由初始化或健康检查暴露。
- **外部输入**：URL、HTTP 方法、Header、Cookie、multipart、JSON、命令行参数、环境变量。

先画出「输入 → 解析器 → 业务逻辑 → 危险 sink → 可观察结果」的路径，再决定是否需要动态验证。

---

## 4. ELF 静态分析

### 4.1 初筛命令清单

对关键 ELF 至少保存：

```bash
file <binary>
readelf -h <binary>
readelf -l <binary>
readelf -Ws <binary>
readelf -r <binary>
objdump -h <binary>
strings -a <binary>
```

重点核对架构/字节序、解释器、装载段、导入符号、GOT/PLT/重定位、危险函数线索、错误字符串和请求处理关键词。

### 4.2 畸形 ELF 处理

厂商 ELF 常畸形：section 表与符号不一致。此时一律走 **LOAD 段** 做 VA ↔ 文件偏移映射，不要信 `.text` 段。公开 PoC 中的硬编码地址只能作为假设，必须与本地二进制、装载基址和运行时日志交叉验证。

---

## 5. 端点枚举

**端点不止在 webroot。** 大量 handler 注册在二进制内（GoAhead 的 `websFormDefine`），webroot 的 goform 目录往往没有对应文件。必须两条腿走路：

1. **webroot 端点**：枚举 web 根目录下的 goform / CGI / 静态路径。
2. **函数表反向推导**：用 GoAhead 的 `formXxx` / `fromXxx` 命名约定，从函数表反向推导二进制注册的端点——否则会漏掉真正危险的目标（Tenda 的 `formexeCommand` 就是这种）。

---

## 6. 危险 sink 与调用链分析

### 6.1 危险函数分类

- **exec 家族**：`system` / `popen` / `exec*` / `doSystemCmd` 等 → 命令注入。
- **mem 家族**：`strcpy` / `sprintf` / `memcpy` / `strcat` 等 → 溢出。
- **格式串家族**：`printf` / `syslog` 用户可控格式串。

### 6.2 传递调用要算 BFS

`handler → helper → system()` 这类间接调用必须沿内部调用图 BFS（建议 MAX_DEPTH=4），否则漏报。不要只看 handler 直接调用 sink。

### 6.3 入口 → sink 数据流

从入口追到 sink，标记数据流和信任边界；再用最小输入验证路径是否真的可达。对地址、符号和版本结论至少保留两个独立证据。

---

## 7. 风险评分与聚焦

对发现的候选做静态评分排序，把动态验证聚焦到 top-N，避免对全部端点（可能上百个）逐个体测拖慢流程。

评分维度（可作为默认参考）：exec 类命中、mem 类命中、格式串命中、是否提取到参数名、是否判定为 preauth。具体权重可按目标调整，关键是**聚焦 + 可复现**，而不是追求分数本身。

---

## 8. 仿真与连通性

### 8.1 系统级仿真优先

优先用系统级仿真（FirmAE / Firmadyne / QEMU system mode）。它完整提供 NVRAM、共享内存、信号量、PID 文件、初始化脚本，才能称为完整复现。网络用 NAT + Host-only 或独立隔离网段，记录启动命令、QEMU/FirmAE 输出、tap/bridge、目标 IP、监听端口到 `logs/emulation_network.log`。

### 8.2 用户态降级（qemu-user）

只在依赖明确且风险可控时用 qemu-user/chroot 单进程。它缺少 NVRAM、IPC 或初始化脚本时，**不能称为完整复现**。用户态仿真常见坑：

- **网桥**：httpd 可能死循环 `ioctl(br0)`，需处理。
- **NVRAM**：修补 `/dev/nvram` → 本地文件（如 `nvram.bin`）。
- **假监听**：`/var/xxx_socket` 等 IPC 需持久化后台进程。

### 8.3 连通性先于触发

触发任何问题前，先运行无害 Web 探测并保存状态码、响应头和页面片段：

```bash
curl -i --max-time 5 http://<lab-ip>/
```

**只有当 IP、端口、固件版本和服务可重复启动都已确认，才进入下一步。**

## 9. 最小非武器化验证

### 9.1 认证边界动态扫描

对枚举出的端点做逐端点认证边界扫描。判定规则：

> 只有**重定向到登录页**（如 `/redirect.html?3`）才算「需认证」。返回正常内容、空响应、或触发崩溃，**都代表未认证即到达 handler 代码**，一律按 preauth 处理。

（该判定仅用于识别攻击面，不代表可进一步利用。）

### 9.2 无害探针确认可达性

对 top-N 的 preauth + exec 候选，用无害探针确认 sink 可达性：

```bash
# 仅示例：确认命令是否被 sink 执行，非利用链
id ; uname -a
```

目标是拿到「sink 可达 / 不可达」的证据，而不是 shell。出现 `uid=0(root)` 之类输出只说明「该 preauth 入口可执行命令」这一事实，用于定位漏洞，不用于武器化。

### 9.3 最小复现梯度

按梯度增加复杂度：

1. **基线请求**：确认正常响应和服务状态。
2. **单变量变化**：一次只改变长度、边界、编码、字段顺序或缺失字段。
3. **观察**：HTTP 状态、响应时间、进程退出、core dump、QEMU 控制台、syslog、内存错误检测器。
4. **重复**：冷启动与热启动各至少一次，记录是否稳定。

若现象是崩溃而非预期行为，先保存崩溃证据并停止扩大输入；不要为了「成功」继续尝试获取 shell。

## 10. 证据与报告规范

每个实验步骤记录：时间、命令、工作目录、输入文件哈希、工具版本、退出码、原始输出路径。建议目录：

```text
firmware/   原始镜像（只读）
work/       解包、切片、临时运行目录
logs/       命令、仿真、探测、崩溃和授权验证日志
reports/    rootfs 盘点、ELF 摘要、阶段证据、交付物检查
```

最终报告固定包含：

1. 范围与授权边界。
2. 目标版本、来源和哈希。
3. 环境与工具版本。
4. 解包与 rootfs 选择依据。
5. 入口、数据流和静态分析证据。
6. 仿真网络与 Web 连通性证据。
7. 最小复现步骤、预期/实际和重复性。
8. 失败尝试与排错判断。
9. **结论置信度**（已证实 / 强线索 / 未证实）及限制。
10. 修复建议、回归测试和后续工作。

「文件齐全」≠「漏洞复现成功」：成功必须同时满足 **版本一致、服务可达、输入可重复、现象可观察、证据可追溯**。

## 11. 常见失败与处理

| 现象 | 优先判断 | 处理 |
|---|---|---|
| binwalk 空目录 | 签名识别或偏移问题 | 保留原日志，人工查魔数并切片 |
| qemu-user 启动即失败 | 运行时依赖/NVRAM/IPC 缺失 | 转系统级仿真，不把单进程输出当成功证据 |
| Web 不通 | 网络、绑定地址、服务未启动 | 先查 IP/端口/bridge/防火墙和启动日志 |
| 地址与公开资料不符 | 固件版本或装载基址不同 | 回到本地 ELF 和运行时映射，停止硬编码猜测 |
| 触发后仅崩溃 | 输入越界线索但尚未证明利用链 | 保存 core/日志/抓包，报告为「崩溃复现」 |
| 结果不可重复 | 隐藏状态或并发/时序因素 | 冷热启动、单变量、缩小输入、记录前置状态 |
