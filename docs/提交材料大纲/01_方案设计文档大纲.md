## 1. 摘要

### 1.1 一句话概括

FirmHound 是一个面向 IoT 固件安全分析的 CLI 智能体流水线，将固件解包、攻击面识别、二进制分析、静态审计、风险评分、反证验证、可选动态验证和证据报告串成可复现流程。

### 1.2 核心价值

- 面向陌生固件，不依赖硬编码 CVE 特征。
- 以 Skill 知识库和确定性 Python 工具链结合，降低专家手工逆向成本。
- 输出结构化证据、决策日志和最终报告，避免“只给结论不给证据”。
- 对外部工具缺失、加密固件、动态验证不可用等情况做诚实降级。

## 2. 背景与问题定义

### 2.1 IoT 固件安全背景

- 智能联网设备规模扩大，路由器、摄像头、网关、工业设备等固件成为攻击面。
- 固件通常闭源、架构多样、文件系统非标准、组件陈旧，传统 Web 扫描器难以覆盖。
- 安全测试从“单点漏洞验证”走向“研发、供应链、合规共同关注”的持续能力。

### 2.2 传统固件漏洞挖掘痛点

- 解包难：非标准 SquashFS、自定义头、加密载荷、嵌套压缩。
- 分析难：MIPS/ARM 等架构混杂，符号缺失，二进制不可读。
- 关联难：Web 参数、启动脚本、二进制危险函数之间缺少自动关联。
- 验证难：静态 source/sink 共现不等于真实可达，误报需要反证。
- 复现难：分析过程常依赖个人经验，缺少可追溯报告。

## 3. 需求分析

### 3.1 比赛要求映射

围绕比赛评分维度写：

| 比赛维度 | FirmHound 对应设计 |
|---|---|
| 任务理解与执行设计 | `fsa plan` 将自然语言任务、固件路径、授权信息解析为阶段计划 |
| 系统架构与工程实现 | CLI、阶段机、ToolRegistry、Schema、EvidenceStore、DecisionStore |
| 决策逻辑与可解释性 | 十维评分、10 问反证、五类结论、证据 ID 追踪 |
| 工具协同与扩展能力 | SaTC、FirmRec、KLEE、mini-BOND 外部轨道与融合机制 |
| 创新与附加价值 | 双轨汇聚、加密固件识别、诚实降级、安全门控动态验证 |

### 3.2 功能需求

- FR-01：支持固件镜像和已解包 rootfs 输入。
- FR-02：支持 `doctor / plan / analyze / status / resume` CLI 命令。
- FR-03：自动识别 rootfs、Web 根目录、启动项、ELF、脚本与配置。
- FR-04：提取 HTTP/CGI/UPnP/启动服务等攻击面。
- FR-05：扫描危险函数和潜在 source-sink 关系。
- FR-06：基于十维评分输出风险等级。
- FR-07：执行反证验证，区分确认漏洞、高置信候选、误报、未知和观察项。
- FR-08：在授权、私有网络、隔离实验室和基线满足时执行无害动态探针。
- FR-09：支持外部分析器可选接入，并在缺失时降级而不中断主链。
- FR-10：生成 Markdown 报告、Schema 化 JSON 产物和决策/证据日志。

### 3.3 非功能需求

- 安全：路径白名单、命令黑名单、私有网段限制、PoC 脱敏。
- 可复现：每次运行以 `run_id` 保存状态、证据和报告。
- 可维护：工具、Schema、Skill 分层。
- 可测试：单元测试、集成测试、CI、多版本 Python。
- 可扩展：外部工具以 adapter/parser/runner 接口接入。

## 4. 总体设计

### 4.1 产品形态

- 产品形态：命令行 CLI，不是 Web 平台。
- 使用对象：固件安全研究人员、实验室学生、比赛现场队员、设备安全评估人员。
- 运行模式：本地离线确定性分析为主，可接国内备案模型或主办方网关增强任务理解与报告辅助。

### 4.2 总体架构

建议写成五层：

1. CLI 交互层：`fsa.cli`
2. 编排决策层：Planner、Engine、StateManager、HumanGate
3. 工具执行层：firmware、filesystem、web、binary、analysis、audit、emulation、external、report
4. 知识与契约层：skills、schemas、config
5. 证据与报告层：runs、EvidenceStore、DecisionStore、report.md

## 5. 核心流程设计

### 5.1 阶段机流程

主阶段：

`INIT -> BASELINE -> UNPACK -> SURFACE -> BINARY_TRIAGE -> DECOMPILE -> STATIC_ANALYSIS -> EXTERNAL_ANALYSIS -> FUSION -> SYMEX_PRUNE -> RANK -> VERIFY_TOP_K -> LOCAL_VALIDATION -> CONSTRAINED_VALIDATION -> REPORT -> DONE`

说明重点：

- `UNPACK` 失败可 fallback 到二进制级分析。
- 外部工具阶段默认非 required，缺工具时降级。
- required 阶段 failed 才中止。
- 每阶段都输出结构化状态。

图表建议：

- 阶段机状态转移图。
- “ok/degraded/failed”三色泳道图。

### 5.2 解包流程

写作要点：

- 支持 binwalk 签名识别。
- 支持经典表格和 `|` 表格格式解析。
- 支持 SquashFS 魔数切片后调用 unsquashfs/sasquatch。
- 支持 UBI、gzip、OpenSSL Salted 加密载荷识别。
- 对 BE3LPro 这类加密固件不伪造成功，而是保存加密切片并提示需要密钥材料。

图表建议：

- “固件解包决策树”：普通文件系统、嵌套压缩、非标准 SquashFS、加密固件。

### 5.3 攻击面识别流程

写作要点：

- 文件系统清单：ELF、脚本、配置、Web 文件。
- 启动链解析：`rcS`、init.d、服务项。
- Web root 枚举：`www/htdocs/webroot_ro` 等。
- Handler 提取：CGI、GoAhead form、UPnP XML、HTTP 环境变量。
- 认证矩阵：预认证、需认证、豁免路由、认证函数证据。

图表建议：

- “攻击面知识图谱”：入口、参数、handler、二进制、危险函数。

### 5.4 二进制与静态审计流程

写作要点：

- ELF 架构识别与安全属性扫描。
- 危险函数扫描：`system/popen/eval/strcpy/sprintf/memcpy` 等。
- Source 分类：HTTP 参数、SOAP 参数、Header、Socket Buffer、配置输入等。
- Sink 分类：命令执行、内存拷贝、格式化字符串、路径/配置注入等。
- 基于规则装配候选调用链。

图表建议：

- “source -> transform -> validation -> sink”链式证据图。

### 5.5 评分与反证验证

写作要点：

- 十维评分：P-I-U-D-C-S-W-K-V-T，满分 30。
- 风险等级：CRITICAL / HIGH / MEDIUM / LOW。
- 10 问人工审计清单。
- 12 条硬规则和五类结论：confirmed-issue、high-confidence-candidate、false-positive、unknown、observation。
- 强调“证据不足不确认漏洞”。

图表建议：

- 十维雷达图。
- 反证验证决策树。

### 5.6 动态验证与安全门

写作要点：

- 四道硬门：AUTHORIZED、LOCAL_LAB、PRIVATE_NETWORK、BASELINE_READY。
- 只允许无害 marker：`id`、`touch /tmp/lab_marker` 等。
- 禁止公网、反弹 shell、持久化、下载执行、破坏性命令。
- 动态验证作为确认增强，不替代授权和人工判断。

图表建议：

- “动态验证安全门”四锁图。

### 5.7 外部分析器协同

写作要点：

- SaTC：Web 参数到危险函数的跨函数静态分析增强。
- FirmRec：已知漏洞复发检测，Blind Run 隔离，不计入零先验发现。
- KLEE：路径可行性/不可达反证。
- mini-BOND：约束导向的安全仿真验证。
- FUSION：外部独有发现转候选；双轨互证提置信；FirmRec 单独隔离。

## 7. 安全与合规设计

写作要点：

- 所有路径来自 `config/*.yaml` 和 `.env`，避免硬编码。
- `config/safety.yaml` 控制路径白名单、命令黑名单、IP/hostname 白名单。
- 日志结构化输出。
- 所有工具输出状态字段，便于恢复和降级。
- 只分析授权固件和本地实验环境。

## 8. 创新点设计

建议写 5 个创新点：

1. 面向固件漏洞挖掘的 CLI 智能体阶段机。
2. Skill 知识库 + 确定性工具链的可复现分析模式。
3. 十维评分 + 反证优先的证据判断体系。
4. 主轨和外部工具双轨汇聚，支持诚实降级。
5. 加密/非标准固件的识别、切片和边界报告机制。

## 9. 可行性与边界

必须诚实写：

- 当前产品主赛道是固件漏洞挖掘，不是覆盖所有渗透测试、应急响应、云安全的泛化平台。
- Ghidra/KLEE/FirmRec/BOND 的真实运行依赖本机工具链和授权环境。
- 加密固件完整解密需要密钥、密码或厂商升级工具逻辑。
- 静态候选不等同确认漏洞，需要反证和动态验证。

## 10. 小结

强调 FirmHound 的最终价值：把不可复现、强专家依赖的固件漏洞挖掘过程，变成可运行、可解释、可回放、可扩展的 CLI 智能体工作流。
