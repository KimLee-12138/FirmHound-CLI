# FirmHound 用户手册大纲

> 定位：让老师、同学或评委能按文档把 CLI 跑起来。语言要比开发文档更“人话”，少讲源码，多讲怎么用、怎么看结果、遇到问题怎么办。

## 0. 欢迎使用 FirmHound

- 产品简介：FirmHound 是一个用于授权 IoT 固件漏洞挖掘的 CLI 工具。
- 适合用户：安全研究人员、竞赛队员、实验室同学、设备安全评估人员。
- 不适用场景：未授权测试、公网攻击、真实设备破坏性验证、无密钥加密固件强行解密。

## 1. 使用前必读

### 1.1 安全声明

- 只分析自己拥有或明确授权的固件。
- 动态验证必须在本地隔离实验室、私有 IP、无害 payload 下执行。
- 系统不会也不应帮助攻击公网目标。

### 1.2 你需要准备什么

- Python 3.11+
- 项目源码
- 至少一个授权固件或已解包 rootfs
- Windows + WSL2 或 Linux
- 可选：binwalk、unsquashfs、sasquatch、qemu

## 2. 安装

### 2.1 Windows + WSL2 推荐路线

步骤：

1. 安装 WSL2 Ubuntu。
2. 执行 `scripts/setup_wsl.sh` 安装 Linux 解包工具。
3. Windows 侧创建 Python venv。
4. 安装 requirements 和 editable package。
5. 运行 doctor。

### 2.2 Linux 路线

步骤：

1. 安装系统依赖。
2. 安装 sasquatch。
3. 创建 venv。
4. 安装依赖。
5. 运行 doctor。

### 2.3 安装验证

```powershell
python -m fsa.cli doctor --json-output
python scripts/dev.py smoke
```

## 3. 快速开始

### 3.1 分析已解包 rootfs

```powershell
python -m fsa.cli analyze <ROOTFS_DIR> `
  --input-type rootfs `
  --depth standard `
  --authorization-holder "team-authorized" `
  --run-id demo-rootfs
```

### 3.2 直接分析固件镜像

```powershell
python -m fsa.cli analyze firmware_samples\router.bin `
  --input-type firmware `
  --depth standard `
  --authorization-holder "team-authorized" `
  --vendor Tenda `
  --model AC15 `
  --run-id demo-ac15
```

```powershell

notepad runs\demo-ac15\report.md
```

## 4. CLI 命令详解

### 4.1 `doctor`

用途：检查本机是否准备好。

常用命令：

```powershell
python -m fsa.cli doctor --json-output
python -m fsa.cli doctor --include-external-probes --json-output
```

怎么看：

- `status=ok`：基础环境可用。
- `commands.available.binwalk=true`：可解包。
- `analyzeHeadless=false` 或 `klee=false`：外部深度工具缺失，不影响基础分析。

### 4.2 `plan`

用途：只规划，不执行。

适合比赛演示“任务理解”：

```powershell
python -m fsa.cli plan `
  --task "分析Tenda AC15固件，授权测试，完整分析" `
  --firmware-path firmware_samples\US_AC15V1.0BR_V15.03.05.19_multi_TD01.bin `
  --authorization-holder team-authorized `
  --depth full `
  --json-output
```

### 4.3 `analyze`

用途：正式分析入口。

参数说明：

- `input_path`：固件文件或 rootfs 目录。
- `--input-type`：`firmware`、`rootfs` 或 `auto`。
- `--depth`：`quick`、`standard`、`full`。
- `--authorization-holder`：必填授权主体。
- `--allow-emulation`：允许隔离动态验证。
- `--vendor/--model/--version`：便于报告展示。
- `--run-id`：指定输出目录名称。
- `--json-output`：机器可读输出。

### 4.4 `status`

用途：查看某次运行。

### 4.5 `resume`

用途：从中断阶段恢复。

## 5. 运行目录和报告解读

### 5.1 输出目录结构

```text
runs/<run_id>/
  state/run_state.json
  evidence/
  decisions/
  artifacts/
  report.md
  final_verdict.json
```

### 5.2 报告重点

读报告优先看：

1. 执行摘要。
2. 任务与授权范围。
3. 解包与根文件系统。
4. 攻击面。
5. 检出候选。
6. 外部分析器结果。
7. 限制与待验证事实。
8. 最终结论。

### 5.3 候选不等于漏洞

- `confirmed-issue`：证据充分。
- `high-confidence-candidate`：高置信候选。
- `NEED_DYNAMIC` 或 unknown：需要动态验证。
- `false-positive`：反证后排除。

## 7. 常见问题

### 7.1 放在桌面上的固件为什么被拒绝？

因为安全策略只允许白名单路径。请复制到 `firmware_samples/`。

### 7.2 为什么缺 KLEE/Ghidra 还能通过？

它们是可选增强工具。基础 CLI 不依赖它们，缺失时会记录 degraded/skipped。

### 7.3 为什么 BE3LPro 没有解开？

该样本检测到加密载荷。没有解密材料时，任何“完整解包成功”都不可信。

### 7.4 为什么系统发现很多候选？

静态扫描偏召回，最终要通过评分、反证、动态验证收敛。

### 7.5 如何给老师演示？

推荐演示顺序：

1. `doctor`
2. `plan`
3. 分析 AC15
4. 打开 report
5. 展示 BE3LPro 加密固件降级
6. 展示 tests/CI

## 8. 安全边界

明确写：

- 禁止未授权目标。
- 禁止公网 IP。
- 禁止破坏性 payload。
- 禁止反弹 shell。
- 禁止把静态候选直接写成已确认漏洞。
